# Walkthrough: one document, end to end

The Week 1 E2 demo. Every number and every JSON block below is generated by
`tools/build_walkthrough.py` from live output, so nothing here describes an
object the code does not produce. Regenerate with:

```bash
python3 tools/build_walkthrough.py
```

**Sample document:** `normal_nrc_reactor_concepts_ch01.pdf`
NRC Reactor Concepts Manual, Chapter 1. 24 pages,
1,291,325 bytes, 18,938 characters of extractable text.

---

## 1. The file becomes a Document

Validation runs first and returns a `ValidationResult`. The `Document` object is
only populated when the file is not rejected, so nothing downstream can
accidentally consume a document that failed import.

```json
{
  "schema_version": "1.0.0",
  "document_id": "doc_72f2433a1e2f2e6340f14040",
  "checksum_sha256": "591a0381163923768eee93a5908e0f1d68e184be4365493c2f05c76df707abcd",
  "source_filename": "normal_nrc_reactor_concepts_ch01.pdf",
  "display_title": "normal_nrc_reactor_concepts_ch01",
  "page_count": 24,
  "byte_size": 1291325,
  "pdf_version": "PDF 1.7",
  "extractor": "pymupdf/1.28.2",
  "import_warnings": []
}
```

`document_id` is `doc_` plus the SHA-256 of the file bytes. It is
content-addressed, which means the same PDF imported twice under two different
filenames is one document, and any byte change produces a different document
rather than silently mutating an existing one.

### The checks that ran

| check | status | message |
|---|---|---|
| `file_nonempty` | pass | File has content. |
| `magic_bytes` | pass | File begins with a PDF header. |
| `parser_opens` | pass | The PDF parser opened the file. |
| `no_open_password` | pass | No open password required. |
| `within_size_limits` | pass | Within size limits. |
| `extraction_permitted` | pass | The document permits text extraction. |
| `structural_integrity` | pass | The document structure is intact. |
| `text_yield` | pass | All pages contain extractable text. |

Every check records what it observed and what it expected, including the ones
that pass. That is what makes the Week 4 regression suite a diff rather than a
rewrite: when a check changes verdict, the report shows the number that moved.

---

## 2. The document becomes a text stream

Text is assembled from layout spans rather than a plain page-by-page dump, and
every character offset maps to a span with a known bounding box **by
construction**. The alternative, extracting text first and searching for
coordinates afterwards, is where highlight drift comes from.

Page boundaries are recorded as offsets into that one stream:

```
page  1  →  chars      0–534   
page  2  →  chars    534–1249  
page  3  →  chars   1249–1652  
...
page 24  →  chars  18067–18938 
```

### Field by field

| field | why it exists |
|---|---|
| `chunk_id` | `sha256(document_id \| chunker_config_id \| char_start \| char_end)`. A pure function of content and config. Not insertion order, not a UUID, not a timestamp. |
| `document_id` | Resolves the citation back to a file without a separate lookup table. |
| `ordinal` | Reading order for display. Deliberately **not** part of identity, so inserting a page upstream does not renumber every chunk downstream. |
| `text` | What gets embedded and what the model sees. |
| `text_checksum_sha256` | Integrity at index time. A chunk whose text stops hashing to this was corrupted in storage or transit, and that is worth catching before it reaches an answer. |
| `char_start` / `char_end` | Offsets into the document stream, not into a page. This is what makes the text reproducible from the source: `text[char_start:char_end] == chunk.text`, asserted in `tests/test_contracts.py`. |
| `page_start` / `page_end` | The citation range a reader sees. |
| `page_spans` | Per-page provenance and highlight geometry. See section 4. |
| `token_estimate` | Context budgeting for E3. A heuristic (chars / 4), labeled as one so nobody builds an exact budget on it. |
| `chunker_config_id` | Makes the chunk self-describing. Given a chunk you can tell which configuration produced it, which matters when a collection is rebuilt with different settings. |
| `chunker_version` | Same, for code changes rather than config changes. |

## 4. Chunks span pages, so `page` cannot be one number

**SDD 5.1 specifies a Chunk as carrying a single page number. On this document
that is wrong for 18 of 19 chunks.**

The NRC manual is slide-style, averaging about
789 characters per page, so a
1200-character chunk covers two to four pages. A single `page`
field would make citations point at whichever page happened to be chosen, and
roughly half of them would point at the wrong one.

| document | pages | chars/page | chunks | chunks spanning pages | share | max pages in one chunk |
|---|---|---|---|---|---|---|
| NRC training manual (baseline) | 24 | 789 | 19 | 18 | 95% | 4 |
| DOE handbook (dense prose) | 96 | 2097 | 202 | 93 | 46% | 3 |
| arXiv paper (two column) | 13 | 3332 | 44 | 14 | 32% | 3 |

It is not an NRC quirk. It shows up on dense prose too, because a chunk boundary
has no reason to coincide with a page boundary.

The fix is `page_spans`: one entry per page the chunk touches. Chunk
`chk_442eb6c07358e762846a8fde` spans pages 1–2:

| page | document offsets | page-local offsets | highlight rects | coords reliable |
|---|---|---|---|---|
| 1 | `0`–`534` | `0`–`534` | 14 | True |
| 2 | `534`–`1195` | `0`–`661` | 18 | True |

Page-local offsets are included so E4 can render one page in isolation without
re-deriving where that page started in the stream.

**Recommendation for the SDD:** change the Chunk record in 5.1 from a page
number to a page range plus per-page spans. Per SDD 17.2 this needs an SDD
update before implementation, and it affects the citation payload E3 finalizes
in Week 6.

## 6. Why the IDs are stable

Run the chunker twice on the same file with the same config and every ID is
identical. Copy the file, rename it, run again: still identical, because identity
is content-addressed rather than path-based.

That is what lets SDD 5.1's promise hold, that historical conversations retain
their original collection version: a citation stored in a conversation three
weeks ago still resolves after the collection is republished, as long as the
document bytes and the chunker config did not change. When either does change,
every affected ID changes too, which is the honest outcome. A stale citation
that silently points at moved text is worse than one that fails loudly.

Proven in `tests/test_contracts.py`:

```
test_same_file_and_config_yield_same_ids   chunk IDs reproduce exactly across runs
test_reindex_preserves_ids                 19 chunk IDs survive re-import under a different filename
test_config_change_changes_every_id        no ID collisions across configs
test_offsets_reconstruct_chunk_text        offsets reproduce chunk text on every chunk
test_page_spans_tile_the_chunk             page spans tile every chunk contiguously
```
